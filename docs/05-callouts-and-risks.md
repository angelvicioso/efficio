# Callouts & Risks

## Risks
| ID | Risk | Impact | Mitigation idea | Status |
|---|---|---|---|---|
| R-001 | **Few ports/terminals offer public APIs.** Many publish data via web portals (often requiring login) or through third-party systems (e.g., terminal operating systems, port community systems). | Could block live data for the POC. | Confirm access early (Q-002); consider a data aggregator; build against a realistic mock first behind the adapter (D-003). **2026-11-25:** Port Houston offers official APIs with registration (D-006), so this is much less likely for Houston. Still open until credentials arrive (Q-019). | Partly mitigated |
| R-002 | **Data is at the terminal level, not the port level**, and formats differ per terminal. | One "port integration" may actually be several. | Start with one terminal; normalize to our own data model. | Open |
| R-003 | **Booking vs. container identifiers.** Before gate-in, terminals know a booking; after, they track containers. | Tracking may break at gate-in if we only store booking #. | Capture container numbers once they appear in terminal data (Q-003). | Open |
| R-004 | **Terms of use / scraping.** Pulling from terminal websites without an agreement may violate terms. | Legal/relationship risk. | Use official APIs, aggregators, or partner agreements only. | Open |
| R-006 | **Receiving windows and cutoffs are usually set per vessel voyage, not per booking.** The booking inquiry reportedly returns "general routing details," which may give the vessel/voyage but not the dates themselves. | We may need a second lookup (the vessel schedule) to show the data from D-008. | Check the API docs once registered (S-013). Design the data model as booking → vessel voyage → receiving window and cutoffs. **2026-11-25:** confirmed by the developer guide: the dates are on the vessel visit, per carrier (`lines[]`). Mapping built. Remaining: the booking → vessel visit link (Q-021). | Mitigated |
| R-007 | **"Booking not on file" is a normal early state.** The carrier sends the booking to the terminal some time after confirming it to the exporter. | Exporters may think the platform is broken, or that something is wrong with their booking. | Show "Not yet at terminal" clearly, keep checking automatically, and alert when it appears. | Open |
| R-008 | **Port Houston's terms of use** may limit how the data is stored, shown or resold. | Could affect the business model. | Orlando confirms with the issuer what Efficio may show to exporters (Q-021); Javier reviews any written terms. **2026-11-25:** permission confirmed (D-027). Keep any written terms on file. | Mitigated |
| R-009 | **Credential handling.** The access document contains the client secret as an image, and the document itself could be forwarded or committed by accident. | Anyone with the secret can query terminal data as us. | Keep the secret in a password manager; use a local `.env` (ignored by git); `.gitignore` blocks `.env` and `.docx` files. Never post credentials in Slack or the docs. Ask the issuer to rotate the secret if the document has been widely shared. | Open |
| R-010 | **The units endpoint only shows containers the terminal already knows about.** Before gate-in, a booking may have no units. | The receiving window and cutoffs (D-008) can't come from units alone. | Use the booking and vessel visit data in N4 (spike S-013). **2026-11-25:** resolved: vessel visits carry the dates before any container arrives. | Closed |
| R-011 | **Port access depends on one person.** The credentials and relationship sit with Orlando. | If Orlando is unavailable, or the credential is tied to him personally, access could stall. | Record the issuer contact in the integration notes; ask whether credentials can be issued to Efficio as a company once the company is formed. | Open |
| R-012 | **No login yet (S-005).** Anyone who can reach the app can see and change every booking. | Exposing real booking data. | Run locally or on a private network only until S-005 is built. **2026-11-25:** logins and per-organization data separation built (D-013, D-014). | Mitigated |
| R-013 | **Super admins can see every customer's data.** | Customers will ask who at Efficio can see their bookings. | Keep the super admin list to the founding team; show a banner whenever a super admin is inside a customer's workspace (built); add an activity log (S-009). | Open |
| R-014 | **No limit on login attempts yet.** | Password guessing once the app is public. | Add rate limiting and lockout before a public launch. **2026-11-25:** 5 attempts, then a 1-hour lockout, with admin unlock (D-021). | Mitigated |
| R-015 | **No email yet**, so invite links are passed by hand and there is no "forgot password". | Links could be forwarded; users who forget a password need an admin. | Links are single-use and expire in 7 days; build S-008. | Open |
| R-016 | **Claimed bookings.** Anyone can type in a booking number, including one that isn't theirs. | Once bookings hold data shared by other parties, someone could see another company's shipment. | P-001: "claimed" links see only port data; "verified" links (confirmed by the carrier) see shared data. **2026-11-25:** built claimed/verified status, carrier verification and removal; parties can't see each other or each other's history. Remaining gap: carriers not on Efficio can't verify anyone. **2026-11-26:** with live data, claimed parties see container numbers and gate times too (D-029, accepted for the POC). | Partly mitigated; accepted for POC |
| R-017 | **Our N4 access returns every company's data** unless a business-unit scope is sent (the API's "instance security"). | A bug in Efficio could show one customer another customer's containers or bookings. | Efficio scopes every query by booking and carrier and never passes raw lists through (P-001); add tests for each new endpoint; ask Port Houston whether credentials can be scoped (Q-021). **2026-11-25: confirmed real** (gate records include shipper names). The live adapter keeps only exact matches and stores a trimmed copy; tested with mixed-company data (D-028). | Open (mitigated in code) |
| R-018 | **Frequent checks vs. Port Houston's rate limits.** Every 5 minutes × every followed booking × (booking + vessel lookups) adds up as customers grow. | Throttling or a blocked API account. | Shared bookings already dedupe lookups; skip sailed vessels (built); get the real limits (Q-021); next steps if needed: fetch each vessel visit once per run for all its bookings, and check far-off bookings less often. | Open |
| R-019 | **Deliberate lockouts.** Anyone who knows a user's email can lock them out for an hour by typing wrong passwords. | Annoyance, not a data risk. | Admins can unlock right away (built). Later: also limit attempts per network address. | Accepted for POC |
| R-020 | **Single data file on a single disk.** | Losing the disk or a bad bug loses the change history and accounts. | D-022/D-031: host snapshots and pre-upgrade copies now; off-site continuous backups before the first real customer (live data went on without them, 2026-11-26). | Open |
| R-021 | **Dependency vulnerabilities.** Third-party packages get security advisories over time. | A vulnerable package in the running app. | Dependabot alerts are on (one handled 2026-11-25, D-025). Check `npm audit --omit=dev` before each deploy; treat production-dependency alerts as urgent. | Open (ongoing) |
| R-005 | **"Real-time" expectations.** Terminal data itself may only update periodically; rate limits apply. | Users may expect instant updates. | Define refresh target (Q-006); show "last updated" on every screen. **2026-11-25:** 5-minute schedule (D-017), "Updates automatically every 5 minutes" and "updated X ago" shown. | Mitigated |
